# 员工对话蒸馏

## 启动与身份

只有用户明确要求开始蒸馏员工经验时，才在知识索引登记阶段与本次范围。现有客服资料仍持续积累。先用已有材料确定：企业/店铺、渠道、商品或业务线、时间段、员工代号与消息角色、目标能力。只询问无法可靠确定的关键缺口。

同名、转接、多人共用账号、主管插话、机器人预回复分别处理；无法绑定的对话可进入团队案例分析，不归因给具体员工。不得凭姓名猜员工身份。评价工作行为，不推断员工性格、健康、背景或其他无关个人特征。

阶段状态使用：尚未启动 / 已启动待绑定 / 候选提炼中 / 验证中 / 已发布。用户已要求开始但范围或员工绑定不足时进入“已启动待绑定”；继续去标识和可观察问题分析，不发布业务范围内经验。后续确认绑定后再推进，不要求重启整个任务。

## 数据整理

- 按稳定员工 ID 或用户确认的精确映射绑定，不能用姓名子串匹配（例如“小李”不可包含“小李助理”）。保留顾客和客服双方以及转接上下文，不能只导出目标员工的句子。图片、语音或撤回信息不可读时保留缺失标记，不把过滤后的文本称完整对话。
- 保留会话及轮次边界，识别顾客/员工/机器人/系统，去除重复导出。
- 顾客标识替换为案例代号；仅保留影响业务判断的订单状态、商品属性等必要事实。
- 原始记录留在用户授权位置，知识库只存去标识的提炼与可定位证据。
- 按场景、难度、渠道、时间、结果分层；好评、差评、失败和转人工案例均应覆盖。
- 分离提炼集与保留评估集。相同会话、同一工单及其近重复不能跨集合；按案件分组，必要时按后续时间段验证。少量材料不强行凑固定数量，报告覆盖缺口。

## 抽取什么

从可观察的行为提炼：如何识别诉求、何时追问、如何解释、如何排查、如何提出选项、如何处理异议、如何判断例外、何时升级以及如何确认解决。个人表达风格可做补充，但不把语气模仿作为主要成果。

每条经验卡：
- 经验 ID、业务范围、触发条件。
- 必需输入与判断顺序、处理动作、回复示例。
- 支持案例与精确轮次、真实结果及未知项。
- 反例与失败条件、业务规则依据、转人工条件。
- 证据等级与状态：单例候选 / 多例支持 / 独立案例已验证。

不设“出现几次就一定正确”的硬阈值。单例可以形成候选；频繁出现的错误应进入反例库。经验与现行规则矛盾时保留案例和冲突说明，不采纳为标准；投诉少、成交高等表面指标不能单独证明有效。

单例已证实严重错误可登记为去标识案例与单例反例候选，两处以案例 ID 互相引用，不计入正向或已验证经验。仅因资料缺失而疑似错误的，登记为待核查案例，不提前称已证实反例。

## 合并为企业能力

对不同员工同一场景的处理逐案比较，控制案件难度和权限差异。可以保留多个条件分支，不强行选唯一话术。团队共通方法进入范围内的 playbooks；有证据的个人优势可保留员工代号标签；未经验证的候选与生效规则分开。

沉淀应具体到：识别信号 → 需要的信息 → 决策分支 → 处理动作 → 对外表达 → 例外 → 交接 → 完成证据。不要只输出人物画像、金句或笼统的“有同理心”。

## 验证与发布

按 quality.md 的保留案例对照验证。审查业务事实、动作完整性、权限与表达；有重大错误的候选先修正。材料不足可以完成候选蒸馏，但必须保持未验证状态。

用户明确授权本次蒸馏与知识更新后，合格且范围明确的条目可写入对应知识文件，不额外逐条请求批准；关键信息冲突的条目挂起，其余继续完成。记录旧版定位、新版本、变更经验 ID、评估案例与结果，保留可回退版本。不得覆盖原始聊天或修改员工绩效记录。

完成报告：处理范围与遗漏、形成的规则/手册/反例、候选与已验证数量、对照结果、剩余证据缺口。未测试的能力不标已掌握，未接入系统不标已上线。

## 近期对话与反馈

“近期”优先按导出文件实际起止日期确定并报告覆盖；数据范围无法确定时再询问。只有收到导出文本不代表拥有平台读取或发送权限。先检查分页、截断、附件缺失、角色映射和重复导出，再按案件分组保留评估案例。若只有几段对话，可以形成未验证候选，不虚构结果或补足不存在的样本。

本地知识更新与向公共仓库反馈是两个动作。用户要求优化自己店铺时，只更新本地范围；明确要求回传时按[反馈闭环](feedback.md)生成候选和去标识反馈包。反馈包不包含真实员工身份、顾客原话全量、订单号码或业务机密；公共仓库不自动采纳任何反馈。
